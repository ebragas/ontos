# Observability

Observability is how operators learn that an [Ontology service deployment](./deployment.md) failed, and how they debug the failure. It uses structured logs, OpenTelemetry traces, and optional error reporting.

## Contract

### Scope

- The Ontology service does not include built-in Action or Function metrics dashboards; operators inspect runtime logs, traces, and fault reports in their configured observability tools.
- Operators export [traces](#traces) over OTLP to any standard OpenTelemetry collector (`OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS`), Sentry, PostHog, or any combination of them, as [Trace export](#trace-export) specifies.

### Logs

- On serverless deployments, runtime logs come from the host platform.
- The Ontology service writes 1 request log for each request that it finishes: one JSON line with these fields.

| Field                        | Value                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `userId`                     | The [user ID](./authentication.md#user-ids) of the caller, when the token passes its checks                                                                                                                                                                                                                                                                                                         |
| `callerKind`                 | The caller kind: `person`, `service` for a [service user](./authentication.md#service-users), `publish` for the publish caller, or `check` for a pull request check. It is set when the signature of the token passes its check, before the read of the permissions                                                                                                                                 |
| `ontologyVersion`            | The Ontology version that served the request                                                                                                                                                                                                                                                                                                                                                        |
| `errorInstanceId`            | The value of the error body, on an error, as [HTTP API](./http-api.md#errors) specifies                                                                                                                                                                                                                                                                                                             |
| `stack`                      | The stack trace of the error, on an error                                                                                                                                                                                                                                                                                                                                                           |
| `route`                      | The route template, on an error                                                                                                                                                                                                                                                                                                                                                                     |
| `routeParams`                | The path parameters of the route, on an error                                                                                                                                                                                                                                                                                                                                                       |
| `errorName` and `parameters` | The `errorName` and the `parameters` of the error body, on an error, with each caller value redacted                                                                                                                                                                                                                                                                                                |
| `mcp`                        | For `/api/mcp` only: `method` (the JSON-RPC method), `tool` (on `tools/call` only), `apiName` (the Object Type, Action Type, or Query Function of the `objectType`, `actionType`, `action`, or `query` argument, when the tool takes one; a short Object Type name becomes its full API name), `clientId` (the `client_id` of the token), and `protocolVersion` (the `MCP-Protocol-Version` header) |
| `body`                       | The request body, only when the request body setting is on                                                                                                                                                                                                                                                                                                                                          |
| `publish`                    | For a publish only: the outcome, the lock wait time, `transactionMs` (the duration of the transaction in milliseconds, when the publish started its transaction), the planned changes, the Ontology version before and after, and the Postgres error code and message on a failure                                                                                                                  |
| `traceId`                    | The trace ID of the request, when its root span records, as [Traces](#traces) specifies                                                                                                                                                                                                                                                                                                             |

- For a service user, the token passes its checks for `userId` when its signature and its claims pass, before the read of its application. So the request log holds `userId` and `callerKind` also when that read then gives 401 or 503. Our rule.
- On an error, the request log holds the `parameters` of the error body. The value of each key that can hold a value that the caller sent (`parameterValue`, `propertyValue`, `primaryKey`, `pageToken`, and `query`) is `"<redacted>"`. The key `query` is redacted for each error, but for a `QueryNotFound`, where it holds the Query API name. Our rule.
- An error parameter that holds a name that the caller sent, such as an unknown parameter name, stays in the request log, because a name is not a value. Our rule.
- A call of a Function's client that fails writes 1 JSON line with the `errorInstanceId`, the `route`, the `routeParams`, the `errorName`, the redacted `parameters`, and the `stack`. Our rule.
- The error line of a failed call of a Function's client also holds `traceId`. It is the trace ID of the request that runs the Function, when its root span records. Our rule.
- `traceId` connects a log line to its trace in each trace destination. Our rule.
- `errorInstanceId` connects the error that an app gets to its request log. For a Vercel time-out or a crash, operators find the request by its Vercel request ID. Our rule.
- A fault of the [token route](./authentication.md#the-token-route) has an `errorInstanceId` in its request log and its error report, but the client never gets it, because the OAuth error body has no such field. Operators find the request by its time, its route, and its Vercel request ID. Our rule.
- A log never holds a token, a secret, or a response body. It holds a request body only when the request body setting is on.
- In Streamable HTTP, each `POST /api/mcp` carries 1 JSON-RPC message, so 1 request log holds 1 MCP call. A 4xx tool error and a 5xx of the [Ontology MCP](./ontology-mcp.md#errors) both put the error fields in the request log. Our rule.
- The request body setting is off by default. The deployment file turns it on for the whole Ontology service deployment, as [Deployment files](./deployment.md#deployment-files) specifies. When it is on, the request log of each request that passes the token check holds its request body as `body`, also for a request that succeeds. The error `parameters` stay redacted. Turn it on only for a deployment that has approval to log customer data. Our rule.
- The request log of the [token route](./authentication.md#the-token-route) never holds its body, also when the request body setting is on, because the body holds the client secret. No span and no error report of the token route holds a field of its body or its `Authorization` header. Our rule.
- An apply that its deadline stops adds no log field and no span kind. Its request log holds the `errorName` `ActionDeadlineExceeded`, and the `stack` of the Postgres error when Postgres stopped the write. Our rule.
- A stack trace keeps the message of its error, so the message can hold any value that the code put in it. Our rule.
- No log line and no error report holds a part of a WorkOS body. When WorkOS answers a read with a body that is not JSON, the error has the fixed message `WorkOS gave the <kind> read a body that is not JSON.` and no cause, because the parse error of the runtime quotes the start of the body. The request keeps its status. Our rule.

### Alerts

- A fault of the Ontology service gets a 5xx. A database error gets 500 `Default:Internal`, also during a Function run, as [Functions](../ontology/functions/functions.md#errors) specifies. An error of the caller, such as a failed Function, gets a 4xx.
- A 5xx can fire error anomaly alerts on the host platform.
- A fault in a tool call of the [Ontology MCP](./ontology-mcp.md#errors) gets HTTP 200, so only its [error report](#error-reports) alerts on it.
- A failed publish or a failed deploy fails its CI run.

### Error reports

- The Vercel adapter reports each fault of the Ontology service to the Sentry project of its deployment, and to PostHog when `TRACES_POSTHOG_REGION` and `TRACES_POSTHOG_TOKEN` are valid. A fault is an error that gets a 5xx, or that ends a streamed answer after its first byte. The Vercel adapter reports no error that gets a 4xx. Our rule.
- The report of a fault that ends a streamed answer holds the route, the Ontology version, the user ID, and the trace link, and the `errorName` `Default:Internal`. It holds no `errorInstanceId`, because the client got no error body. A client that stops reading is not a fault, and gets no report. Our rule.
- On the MCP route, a tool error that comes from a 5xx of its route is also a fault, and gets 1 report, as [Ontology MCP](./ontology-mcp.md#errors) specifies. Our rule.
- A failure of the engine changes at cold start gets 503. A 5xx of a call of a Function's client gives the Action 500, as [Functions](../ontology/functions/functions.md#errors) specifies. So each one gets 1 report, with the `errorInstanceId` of the answer that the caller got. Our rule.
- Each report holds the `errorInstanceId` of the error body, the `errorName`, the route, the Ontology version, and the user ID and the caller kind when the signature and the claims of the token passed their checks, also when the read of the application of a service user then gave 401 or 503. Its environment is `ONTOLOGY_ENVIRONMENT`, and its release is the version of the service package. In PostHog, the distinct ID is the user ID when present, and personless when absent. Our rule.
- A report of a fault on `/api/mcp` also holds the `method`, `tool`, `apiName`, and `clientId` of the `mcp` field as tags in Sentry and properties in PostHog. Our rule.
- A report holds no token, secret, request header, request body, or response body, as [Logs](#logs) specifies for a log. The Vercel adapter turns off each kind of data collection of the Sentry SDK that can hold them, keeps no breadcrumbs, and removes the request from each Sentry event. For PostHog, it turns off GeoIP, exception autocapture, and tracing headers, and removes request, header, cookie, body, and IP properties in `beforeSend`. Our rule.
- The Vercel adapter sends PostHog fault reports to `https://<region>.i.posthog.com` from `TRACES_POSTHOG_REGION` only, and never to a custom host. Invalid trace variables report at cold start to Sentry only, and invalid PostHog variables turn PostHog fault reporting off. A failure or timeout of PostHog never changes the HTTP response or Sentry fault reporting. Our rule.
- The Vercel adapter sets the `tracePropagationTargets` of the Sentry SDK to an empty list. So the SDK adds no `sentry-trace` and no `baggage` header to an outbound request, such as a request to the AuthKit domain or to WorkOS. Without it, the `baggage` header gives each outside host the Sentry environment, the release, the DSN public key, and the trace ID. Our rule.
- After a fault before the answer, the Vercel adapter passes 1 bounded flush promise to `waitUntil` when at least 1 enabled destination received a report, and none when neither did. It flushes Sentry for at most 2 seconds, PostHog for at most 2 seconds, or both together, and calls no per-request PostHog shutdown. For each request that matches a route, it also passes to `waitUntil`, inside the request, a promise that waits up to 60 seconds for the body to end, and flushes only when a fault that ends a streamed answer was reported. Sources: [`@vercel/functions`](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package) ("Extends the lifetime of the request handler for the lifetime of the given Promise"), [Draining](https://docs.sentry.io/platforms/javascript/guides/node/configuration/draining/) ("Flushes all pending events").
- When the root span of the request records, each report also holds the tag `trace_id`, the Sentry trace context of the root span, and the PostHog `$trace_id` and `$span_id` properties. When the root span does not record, the Vercel adapter removes `$trace_id` and `$span_id` from the PostHog event. Our rule.
- Sentry links a report with this trace context to its trace, also with `enableOpenTelemetrySetup` off, and PostHog links `$exception` events with `$trace_id` and `$span_id` to their traces. So an issue leads to its trace.
- The `node:http` adapter reports nothing.

### Traces

- The Ontology service records 1 trace for each request that matches a route. The trace has 1 root span and 1 named span at each seam of the request, so an operator sees where the time of the request went. Our rule.
- The service writes spans with the OpenTelemetry API, and exports them over OTLP, as [Trace export](#trace-export) specifies. It uses no automatic instrumentation of `http`, `fetch`, or `pg`, because automatic spans record URLs and values. Our rule.
- Each call of `fetch` in `src/` during a request runs inside a named span other than the root, so each outgoing call gets its own span. The route tests of the `sql` project check it: their guarded `fetch` fails each call that runs with no such span. Our rule.
- The span catalog, `packages/service/src/spans/catalog.ts`, is the one list of spans. For each span name, it gives the `fixed` constants including `sentry.op`, the attribute kinds at the start (`start`) and later (`later`), and the required child spans (`requires`). The attribute types, the attribute filter, and the check of required spans all come from the catalog. This doc names the seams and does not copy the catalog. Our rule.
- A span holds its name, its start and end times, its status, and the attributes that the catalog declares for its name. No span holds a token, a secret, a header, a request body, or a response body. No span holds a SQL parameter value, a URL, a WorkOS response, an error message, or a stack trace. Our rule.
- No attribute takes a plain string. Each attribute kind is a number, a boolean, a union of literals, the route key, or 1 of 3 brands. Only the `spans` module makes a brand. Each maker takes a typed source: `sqlTemplate` takes a SQL statement, `apiNameOf` takes a compiled Object Type or Action Type, and `tracedUser` takes a caller. So `tsc` refuses a value from a request in an attribute. Our rule.
- `sqlTemplate` reads only the text of a SQL statement, never its values. It records only the verb of a DDL statement, such as `CREATE TABLE`, because a schema migration of a publisher can hold a literal. In each other statement, it replaces each string, dollar-quoted, and number literal with `?`, and keeps at most 4096 characters. Our rule.
- A span that ends with an error gets the status ERROR and the attribute `error.type`. Its value is the `errorName` of an `ApiError`, or the class name of another error. A thrown value that is not an error gives `NonError`. The span records no message and no stack trace, because a message can hold a value. Our rule.
- At run time, the `spans` module drops each attribute key that the catalog does not declare for the span name, and each value of the wrong kind. It counts each drop in the attribute `spans.dropped_attributes`. A test that records a span with a drop fails. Our rule.
- Code adds a span in 1 way: `span(name, attrs, run)`. `run` returns a value, a promise, or an async iterable. The span ends when the value returns, when the promise settles, or when the iterable ends, throws, or is closed. `s.set` adds a `later` attribute. Our rule.
- `s.bind(bridge)` binds the `fetch` bridge of a Function's client to the `function run` span of the current request. So the spans of a Function's client calls join the trace of the request that runs the Function, also on a warm worker that another request started. Our rule.
- The worker script loads no OpenTelemetry package. It sends its own times, the bundle load and the function body, in its answer to the main thread. The `worker call` span records them as child spans with explicit start and end times through `live.record`, and `live.record` applies `CATALOG[child].fixed`. Only the `worker call` span uses `live.record`. Our rule.
- With no tracer provider, each call of the `spans` module records nothing and returns the result of `run`. So the `node:http` adapter and the test service record no trace. Our rule.
- The root span starts in `handle` after the route match. Its name is the route key, the method and the route template, such as `GET /api/v2/ontologies/{ontology}/objectTypes`. A request that matches no route records no trace. Our rule.
- The root span ends when the response body closes, errors, or is cancelled. A child span `response.body` covers the time of the body after `handle` returns. A response with no body ends the root span when `handle` returns. Our rule.
- The root span holds the route key, the access kind, the HTTP status, and the Ontology version. It also holds the user ID and the caller kind of the caller when the signature of the token passed its check, before the read of the permissions. So a `401` of a deleted application and a 503 of WorkOS still record who called. On `/api/mcp` it also holds the JSON-RPC method and the tool, as known literals. Our rule.
- Each route row of the route table has a required field `spans`. It names the child spans of the root that each 2xx answer of the route must have. The catalog names the required children of each other span in `requires`. Our rule.
- The route tests through `handle` check each trace after each test. The trace must have 1 root, no span with a lost parent, and each child span inside the time of its parent. A `workos read` span of a WorkOS read that requests share can end after the root span of the request that started it, because the read keeps its own time limit, as [Permissions of a caller](./authentication.md#permissions-of-a-caller) specifies. It must have each required span, and no span may hold a `CANARY` value of the caller input. `ROUTE_FIXTURES` is a record keyed by the route key, so `tsc` refuses a route with no trace fixture. The route key type comes from `ROUTE_KEYS` in the span catalog, and a 2-way `tsc` check keeps that list equal to the route table. Our rule.
- The token check gets a `token check` span. A fetch of the JWKS on a key cache miss gets a `jwks fetch` child span. Each read of WorkOS gets a `workos read` span with its kind and status, and no URL. Our rule.
- The call of the [token route](./authentication.md#the-token-route) to the AuthKit token route gets a `workos token` span with its status, and no URL. Our rule.
- Each request that opens an Ontology gets an `ontology view` span, with `ontology.cache.hit` and the Ontology version. A compile of a product version on a cache miss gets an `ontology compile` child span. Our rule.
- The request that runs the cold start gets a `cold start` span with the role `ran`, and the spans of its engine changes and compiles. A request that waits for that run gets only a `cold start` span with the role `joined`. On a tool call, the `cold start` span is a child of the `mcp tool` span. The root span of each of these requests gets `ontology.cold_start`. After the cold start passes, no request gets a `cold start` span. Our rule.
- 1 helper wraps each of the 5 SQL sites of the `db` module: `query`, `stream`, `transaction`, `snapshot`, and the `Db` inside a transaction. Each statement gets a span with its `sqlTemplate`. The wait for a pool connection gets its own span. A statement inside a transaction or a snapshot gets `held`. Our rule.
- A Function run gets a `function run` span, with a `worker wait` child for the wait for a worker and a `worker call` child for the call. Each call of a Function's client gets a `function client` span, named by its route key, with its SQL spans. Our rule.
- The root span of an Action apply, both rule-backed and function-backed, records `action.api_name`. The `function run` span has `function.api_name` and `function.kind`, `edit` or `query`. The run of an edit Function also keeps `action.api_name`. The request log records a [Query Function](../ontology/functions/query-functions.md#run) run as it records a Function call in an Action. Our rule.
- A `tools/call` of a tool that the Ontology MCP lists gets an `mcp tool` span. The MCP SDK refuses a call of an unknown tool before the tool runs, so that call gets no `mcp tool` span. Each route that the tool runs gets an `mcp route` span, named by its route key, with the spans of that route. The `mcp` module records no span. Our rule.
- Each [derived property](../ontology/object-link-types/derived-properties.md) that a `loadObjects` or an aggregate computes gets 1 `derived property` span. The span holds the form, `objectType` or `request`, and the reason: `select`, `requestFlag`, `setting`, or `query`. `query` is a value that a `where` clause, an `orderBy`, a metric, or another derived value reads, and that the page does not return. The span also holds the hop count, the sum of the hops of its selections, and the operation. An expression gives the operation `expression`. An Object Type derived property also gives its API name. A request derived property gives its position in its `withProperties` clause, and no name, because the caller chose the name. Our rule.
- The root span of a read that computes a derived value holds 3 counts: `derived.count`, the count of derived values, `derived.objects`, the count of Objects of the page, and `derived.sql_ms`, the SQL time, from the first read of the SQL stream to its first row, or to its end when it has no row. An aggregate reads no Objects, so it gives no `derived.objects`. A read of a Function's client has no root span of its own, so it records the `derived property` spans and no counts. No span holds a derived value or a primary key. Our rule.
- Each attempt of an apply gets an `apply attempt` span with its number. A rule-backed apply that retries gets 1 span for each attempt. Our rule.
- The `apply attempt` span of an attempt that reaches the write gets `apply.object_edits`, the count of Object edits that the attempt writes. The edits [compile](../ontology/action-types/rules.md#compile) to 1 edit for each Object, so the count is the number of Objects that the attempt creates, modifies, or deletes. The count leaves out Link edits. An attempt with no Object edit gets 0. The attempt sets the count before the write, so an attempt that the deadline or the version check stops keeps it. An attempt that stops before the write, such as `VALIDATE_ONLY` or an `INVALID` answer, has no `apply.object_edits`. Our rule.
- A publish gets a span for each step: the read, the plan, the store, and the lock wait. The transaction of a publish gets an `upgrade installation` span for each installation, with its lock wait and an `upgrade step` span for its step. Our rule.
- When a request matches a route and sends a valid W3C `traceparent` header, the root span adopts that `traceId` and `parentSpanId` at its start, after the route match and before the cold start and the token check. So `cold start` and `token check` stay child spans of the root span. A missing or malformed `traceparent` header starts a fresh trace ID. The incoming `sampled` flag never sets the sample choice. Our rule.

### Trace export

- The tracing layer (`packages/service/api/_tracing.ts`) exports spans over OTLP to any combination of a standard OTLP/HTTP collector (`OTEL_EXPORTER_OTLP_ENDPOINT` and optional `OTEL_EXPORTER_OTLP_HEADERS`), Sentry (`TRACES_SENTRY`), and PostHog (`TRACES_POSTHOG_REGION` and `TRACES_POSTHOG_TOKEN`). Each destination is on only when its optional variables are set, as [Deployment files](./deployment.md#deployment-files) specifies. When multiple destinations are enabled, each receives the same sampled spans. Our rule.
- With no destination on, the tracing layer registers no tracer provider. Our rule.
- The standard OTLP destination sends protobuf traces to `OTEL_EXPORTER_OTLP_ENDPOINT` (appending `/v1/traces` when absent) with any headers parsed from `OTEL_EXPORTER_OTLP_HEADERS`. Our rule.
- The Sentry destination reuses the required `SENTRY_DSN`, with its own opt-in, `TRACES_SENTRY`, because the DSN stays required for error reports. `getOtlpTracesEndpoint(dsn)` of `@sentry/node` gives the OTLP URL and the `X-Sentry-Auth` header, so Sentry traces need no new secret. Source: `getOtlpTracesEndpoint` in `@sentry/server-utils` 11.8.0, which `@sentry/node` 11.8.0 exports.
- The PostHog destination takes a region, `us` or `eu`, and a project token that starts with `phc_`. The Vercel adapter makes the OTLP URL from the region only, so a hand edit cannot send spans to another host. The URL is `https://<region>.i.posthog.com/i/v1/traces`, with the header `Authorization: Bearer <token>`. Our rule. Source: [Getting started with distributed tracing](https://posthog.com/docs/distributed-tracing/start-here.md) (`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT="https://us.i.posthog.com/i/v1/traces"`, and `https://eu.i.posthog.com` for an EU project).
- PostHog keeps the spans of the OTLP export and makes traces readable back. Source: [Node.js tracing installation](https://posthog.com/docs/distributed-tracing/installation/nodejs).
- The deployments and environments of the Ontology service can send their spans to 1 shared PostHog project. The resource of each span holds `service.version`, `deployment.environment.name` (the value of `ONTOLOGY_ENVIRONMENT`), and `ontology.deployment` (the host of `ONTOLOGY_BASE_URL`), so a view tells the deployments and environments apart. Our rule.
- The sampler uses `TraceIdRatioBased(rate)` for the root and for each remote parent. The rate is `TRACES_SAMPLE_RATE`, from 0 to 1, and it is 1 when the variable is not set. So at today's volume each request records a trace, and an incoming `traceparent` flag never overrides `TRACES_SAMPLE_RATE`. A local child of an unsampled root records nothing. Our rule.
- The Vercel adapter starts the tracer provider before `Sentry.init`. `Sentry.init` keeps `enableOpenTelemetrySetup` off and sets no `tracesSampleRate`, so Sentry registers no tracer provider of its own. Source: `getClientOptions` in `@sentry/node` 11.8.0 (`enableOpenTelemetrySetup: options.enableOpenTelemetrySetup ?? false`).
- With a destination on, each request with a recording root span passes 1 promise to `waitUntil`. The adapter finds the root span by `route.key`, so a root span with a remote parent from `traceparent` still flushes. The promise waits for the end of the root span, for at most 60 seconds. Then it calls `forceFlush` of the span processor of each destination, each for at most 3 seconds. A catch logs only the kind of the destination that failed. So the spans leave after the body ends, and a body that never closes does not hold the instance to its `maxDuration`. Source: [`@vercel/functions`](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package) ("Extends the lifetime of the request handler for the lifetime of the given Promise").
- With no destination on, or for a request that the sampler drops, the Vercel adapter passes nothing to `waitUntil` for traces. Our rule.
- A trace variable in Vercel with a bad value turns its destination off. A bad `TRACES_SAMPLE_RATE` applies to each destination, so it turns each one off. The service keeps serving, and sends 1 Sentry error report at cold start that names the variable and not its value. The CLI refuses each bad value at deploy, so only a hand edit in Vercel can cause it. Our rule.
