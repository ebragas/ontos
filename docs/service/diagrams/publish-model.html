Publish in 1 transaction: a model check

This page verifies the publish, install, restore, and reconcile logic with a TLA+ model checked by TLC.

This TLA+ model describes the publish, install, restore, and WorkOS reconcile implementation. Each action of the model names the code that it describes: the check (publishOntology, checkWorkos), the WorkOS additions (planWorkosSteps), the transaction (transact, lockRows, runChain), the reconcile (reconcile, planReconcile), the answer, the CLI job (sendPublish, releaseSdkPackage), installOntology, the copy and the switch of a restore (restoreSwitch), and dropSchema. The transactions are read committed, as db.transaction opens them.

In short: with 1 publish job at a time, each rule holds, except in the known cases documented in ADR 0015 and in 1 state that the spec allows (path 6). A job can exit 1 for a version that is stored (known case 2), and then the roles can stay on the older file until a rerun. 2 publishes at one time, after a job ends while its request still runs, can leave a default role with a wrong list or release the SDK package of an older version (known case 1). No path loses data. TLC found no bug of the code outside these cases. Each bug path is replayed against the code in packages/service/src/publish/modelPaths.sql.test.ts, and path 5 also in packages/cli/src/publishModelPath.sql.test.ts.

Known cases that stay open

ADR 0015 documents these accepted cases. The repair for each one is a rerun of the failed publish job, or the next publish when no job failed (paths 4, 5, and 8). Rules 11a and 11b check the repair by a rerun.

  • Known case 1. Paths 3, 4, 5, and 8. Each needs a job that ends while its request still runs, and a next job. A cancel or a lost HTTP answer can end the job while its request runs. Without a job that ends while its request runs, these rules hold (GhostNoCancel run, 3,555 states).
  • Known case 2. Paths 1, 2, and 7. The service stops after its commit, the reconcile fails after the commit, or the answer to COMMIT is lost.
  • Allowed by the spec. Path 6: an added permission stays after a stop until a later reconcile.
  • No data loss. Rules 1, 2a, 3, 4, 8, 9, 10, and the extra rule hold in each safety run, the variant runs too.

Rules

Each count is the count of distinct states of a complete TLC run, unless the row says "breaks at". When a rule breaks, TLC runs again without that rule, so the count of a holding rule is that of the run that checked it. "Breaks at" gives the states that TLC found when it stopped at the first break, in 1 run. TLC runs with several workers, so that count changes from run to run.

  • WorkOS run. 4 starts: no version (the first publish), 1 version, 2 versions where only the older names r2, and a newest grants file that does not parse. Each role starts absent from WorkOS or with any list. 2 grants files to publish, 3 job runs, new pushes, cancels, and 2 faults.
  • Data run. 2 stored versions, 1 installation, an install of a second one, a restore with a copy on each stored version, a drop, saved data, table changes or none, 3 job runs, and 2 faults.
  • Ghost run. The service runs 2 requests: a canceled job keeps its request, and the next job starts. 2 job runs and 2 faults. GhostNoCancel is the same with no cancel.
  • Liveness runs. Fairness: while a normal step can happen, one happens. A person reruns a failed job, and an admin fixes saved data before the rerun. 4 job runs and 2 faults. The WorkOS runs start with each role absent or with any list. The rules about the old page wording of rule 5 and rule 6 also run on a start where WorkOS equals the newest file.

A fault is a WorkOS failure, a stop of the request, a lost answer to COMMIT, the 60 s limit or a Postgres error, a lock wait that ends, a cancel, or saved data that blocks a step.

Rules 2a and 9, and the last part of rule 8, hold by the shape of the code. A transaction writes nothing that another actor sees until its commit, and a row names a copy only in the commit of its switch. The model keeps these rules so that a fault can show them break.

Rule 10: each lock wait in the model ends when the holder releases the lock, or through a fault (the 5 s lock_timeout, the statement limit of an install, or the 90 s wait of a switch). So with no fault left, a cycle of waits shows as a deadlock, and TLC found none. TLC counts no seconds, so the lengths come from the code.

Bug paths

Each step is 1 action of the model, in the words of the chart. Each test replays its path against the code on Testcontainers Postgres. Each test of modelPaths.sql.test.ts runs as a role that is not a superuser, with the WorkOS stub. The CLI test runs node.ts as the superuser role of the test Postgres. A Db wrapper makes a lost answer to COMMIT, and a held WorkOS call keeps 2 requests apart. Each test passes, so each path occurs in the code. A stop of the service is replayed as a Fault of the WorkOS port, or a thrown error of the Db. After it, the code still tries the reconcile and answers 500, where a real stop gives no answer. The stored version and the roles end the same.

Path 1: rule 2b, known case 2

The first publish commits, and the service stops the request before the reconcile. The job exits 1, version 1 is stored, and no default role has its permissions.

Steps: a person starts the job; the check reads the data; the check reads WorkOS; the check passes; the transaction starts; gets the lock of the versions; inserts the version; Postgres commits; the service stops the request.

Test: path WorkOS.1, and path WorkOS.1b for a lost answer to COMMIT after Postgres committed, in packages/service/src/publish/modelPaths.sql.test.ts. On the first publish, no default role has a permission until the rerun, so no person can install. The rerun stores no new version, creates r1, and gives it p1.

Path 2: rule 5, any end, known case 2

The answer to COMMIT is lost. The reconcile reads the stored versions before Postgres applies the COMMIT, so it sees no version and writes nothing. Then Postgres commits. The service answers 500, and the roles stay on the older file until a rerun. In the worst case of this window, a default role lacks a permission that the newest version adds, and still holds a permission that the newest version drops. The model shows both, and the second test of this path shows both on the code: after version 1 gives r1 p1, a publish of a file that gives r1 p2 ends with r1 holding p1 and not p2. A rerun stores no new version, runs the reconcile, and each default role then equals the newest stored grants file.

Steps: a person starts the job; the check reads the data; the check reads WorkOS; the check passes; the transaction starts; gets the lock of the versions; inserts the version; the answer to COMMIT is lost; the reconcile reads the versions; Postgres commits after the lost answer; the reconcile reads WorkOS; the reconcile ends.

Test: path Ghost.8, in packages/service/src/publish/modelPaths.sql.test.ts.

A late COMMIT after a rerun. The runs above let a late COMMIT land only while its request runs, or during the job run that sent it. A variant run removes that limit. In the path that it finds, a COMMIT whose answer was lost lands after the job exited 1, a person reran it, a WorkOS addition of the rerun failed, and the reconcile of the rerun read the version before. Then version 2 is stored, and the roles stay on the file of version 1: the state of known case 2, which a second rerun repairs. On GhostNoCancel, beyond the 4 rules that break in the main run, the variant breaks only rule 5 after a seen end, at 3,041 states in 1 run. With those 5 rules removed, each other rule holds (4,033 states). On the data run, the variant reaches the same 10,084,648 states, and each data rule holds. That data run has 1 request slot, and a new request needs the slot of the old one to have no open COMMIT, so it gives no evidence about a late COMMIT after a rerun. In the code, a COMMIT can land late only while it is on its way to Postgres (inference). The transaction_timeout of 60 s ends a transaction whose COMMIT does not arrive in time, so a COMMIT cannot land later than that (inference from the Postgres rules).

What the model leaves out

  • 1 product, 2 installations at most, 1 restore, 1 install, and 1 drop.
  • 2 default roles and 2 permissions. The model has no permission create or description, no RoleInUse check, and no Organization role.
  • A step is 1 action, and the table locks of 1 installation are 1 lock. Each pair of schemas has 1 flag for data that the next step rejects. The check reads only that flag. Reserved names, the OSDK set, the column limit, the product RID, and validateOnly are not in the model.
  • A late commit after a lost answer lands only while its request runs, or during the job run that sent the COMMIT. A late rollback can land at any time.
  • The copy of a restore always passes, from a source on any stored version. The source branch is a fixed point in time, so its row and its data agree. The checks of engine changes, schema owner, and row number are not in the model. A stop of the restore script is not in the model.
  • The engine-change catch-up of a request, the cold-start check, the remap, the staging reset, and a release rollback are not in the model.
  • Requests that read data are not in the model. Rule 9 reads the registry row in their place.
  • Time has no clock. Each limit is a step that can occur while its wait or its transaction is open.
  • 2 publishes at one time come from any job that ends while its request still runs: a canceled job, or a job whose HTTP answer is lost and that a person runs again (checked on node.ts by an independent probe, below). The model has 1 action for both: the job ends, and its request runs on. The queue of the managed workflow keeps the other jobs apart.

What TLC checked, and what is an inference

  • TLC checked each rule of this page on the model, with the state counts above.
  • That the model matches the code is an inference from reading the code. The 11 replay tests confirm it for each bug path. The probes confirm that each part of the model is reached.
  • That a COMMIT which reached Postgres commits at once, and that transaction_timeout limits how late a COMMIT can land, are inferences from the Postgres rules. The variant run above checks the rules without that limit.
  • That a lost HTTP answer leaves the request running was checked on node.ts by an independent probe of the verifier: a publish held in its transaction by a row lock, a client socket that ends (the CLI exits 1), then the release of the lock. Version 2 committed, the installation moved, and the reconcile ran. It is not checked on the Vercel runtime, and not for a cut during the check or the additions. The publish route passes no abort signal (handler/index.ts), and sendPublish has no catch, so the job exits 1 and the operator reruns the publish job.
