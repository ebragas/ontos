Default roles in WorkOS: model of publish and upgrade

This page describes the design before ADR 0015. That design had a removal step, an upgrade of each installation after the store, and a hold. The Ontology service no longer has them: a publish upgrades every installation in 1 transaction, and a reconcile makes each default role equal to the newest grants file. So the paths of this page about a held or behind installation do not apply. The publish model gives the model check of the design of today.

A publish copies the default role of its grants file to WorkOS before the store. Each installation then upgrades at its own time, and the removal step takes permissions from the role at the end of a pass. This TLA+ model checks if each member keeps the correct access during that time. It has 2 Organizations, each with 1 installation (I1 and I2) of 1 product, 1 default role, 2 Object Types (T1 and T2), and the permissions a, b, and c. An operator can hold and release I2. A member sees each type whose permission, in the grants file of its own installation's version, the role holds in WorkOS. The model comes only from the text of Publish, Publish job, The grants file, and Access. TLC checked this model against that design.

Grants files

v1 is installed, and the role in WorkOS matches it. Each sequence then publishes v2 and v3. The notation T1:a means that T1 needs the permission a.

Sequence v1 v2 v3
Drop in place T1:a, T2:b. Role: a, b. T1:a, T2:b. Role: b. T1 keeps a, and the role loses a. Same as v1. The role gets a back.
Split drop T1:a, T2:b. Role: a, b. T1:c, T2:b. Role: b, c. T1 moves to the new c, and the role loses a. T1:a, T2:b. Role: b. T1 moves back to a. The end is the v2 of the drop sequence.
Move T1:a, T2:b. Role: a. T1:b, T2:b. Role: b. T1 moves to b, which exists already. T1:c, T2:b. Role: c. T1 moves to the new c. The role loses b, and T2 keeps b.

Rules

The results are for the current text of Default roles in WorkOS, which settles 3 readings: the WorkOS steps add each permission that the role lacks, PermissionInUse compares with the role in WorkOS, and the store runs PermissionInUse again. The model has 382 states for the drop sequence, 766 for the split drop, and 972 for the move.

  • Holds. No loss: a member keeps each type that its own version gives to its role. The spec accepts 1 case: an installation held after the store of a version that takes the permission, while a type of that version still needs it. It breaks under the earlier text (paths 3 to 5).
  • Holds. No over-grant: a member never uses a type through a permission that a newer version took from the role, and that its own version does not give. The spec accepts the time from the store to the removal step of that version, also across a stopped job. This result needs only 1 held installation. See "What the model leaves out".
  • Breaks. No early grant: a member never uses a type that its own version keeps from its role, through a permission that a newer version gives. The model accepts the time before the store and the time until the installation upgrades. Paths 1 and 2. The specification accepts both paths.
  • Holds. Converge: after a removal step with no hold, the role in WorkOS holds exactly the permissions that the newest version gives it. It breaks if the WorkOS steps add only new permissions (paths 6 to 8).
  • Holds. No store before its WorkOS steps: at each store, WorkOS has each permission of the version, and the role holds each permission that the version gives it. It breaks if the WorkOS steps add only new permissions (paths 6 to 8).
  • Holds. No deadlock: each state has a next step.

Bug paths

Each path is the shortest path that TLC found. Step numbers are those of TLC.

  1. No early grant (Drop in place sequence, 17 steps). A held installation gets back a type that its own version took.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a and b.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes.
    6. The WorkOS steps end.
    7. The store saves v2.
    8. The pass upgrades I1 to v2.
    9. The pass upgrades I2 to v2.
    10. The removal step removes a from the role.
    11. A developer pushes v3.
    12. The publish job starts with its catch-up pass.
    13. The removal step runs and removes nothing.
    14. The publish check passes.
    15. WorkOS adds a to the role.
    16. The WorkOS steps end.
    17. The store saves v3.
    18. An operator holds I2 on v2. Its members use T1 through a, but v2 does not give a to the role.

    The access lasts while the hold lasts. The specification accepts it. The current text does not change this path. Its run finds a variant of the same length, in which the job stops after the store of v2.

  2. No early grant (Move sequence, 8 steps). A held installation gets a type that its own version keeps from the role.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes.
    6. WorkOS adds b to the role.
    7. The WorkOS steps end.
    8. The store saves v2.
    9. An operator holds I2 on v1. Its members use T2 through b. The role of v1 holds only a, so v1 keeps T2 from them.

    The access lasts while the hold lasts. Before the hold, the same access is in the window that ends when I2 upgrades. The current text does not change this path.

Paths that the earlier text gave

The text of Default roles in WorkOS was updated during this model check. The revised text runs PermissionInUse again under the store lock, and compares with the role in WorkOS. Each of these paths breaks No loss under the earlier text, and the revised text closes it.

  1. No loss (Drop in place sequence, 9 steps). A hold between the check and the store of a drop in place.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a and b.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes. No installation is held, so PermissionInUse finds nothing.
    6. The WorkOS steps end. They add nothing.
    7. An operator holds I2 on v1.
    8. The store saves v2. The store checks only for a behind installation.
    9. The pass upgrades I1 to v2.
    10. The removal step removes a from the role, because T1 of v2 still needs a. The members of I2 lose T1, which v1 gives them.

    The spec accepts this loss only for an installation that stops after the store. Here the hold came after the check and before the store. The current text runs PermissionInUse again under the store lock, which refuses this store.

  2. No loss (Split drop sequence, 19 steps). The same drop in place, split over 2 publishes, gets past PermissionInUse.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a and b.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes.
    6. WorkOS creates the permission c.
    7. WorkOS adds c to the role.
    8. The WorkOS steps end.
    9. The store saves v2.
    10. The pass upgrades I1 to v2.
    11. The job stops.
    12. A developer pushes v3.
    13. The publish job starts with its catch-up pass.
    14. An operator holds I2 on v1.
    15. The removal step keeps a, because I2 on v1 uses it and v2 does not declare it.
    16. The publish check passes. It compares v3 with the grants file of v2, which already lacks a. So v3 takes only c, and v3 does not declare c.
    17. The WorkOS steps end.
    18. The store saves v3.
    19. The pass upgrades I1 to v3.
    20. The removal step removes a, because T1 of v3 needs a. It removes c, because no installation uses c. The members of I2 lose T1. I2 was held before the check.

    The stop at step 10 is not necessary. A run with I2 held from the start, with no stop and no release, breaks No loss in 18 steps. In 1 publish, the check refuses this change with PermissionInUse. The current text compares with the role in WorkOS, which still holds a, so it refuses v3 here.

  3. No loss (Move sequence, 21 steps). A hold between the check and the store, when v3 takes b and T2 still needs b.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes.
    6. WorkOS adds b to the role.
    7. The WorkOS steps end.
    8. The store saves v2.
    9. The pass upgrades I1 to v2.
    10. The pass upgrades I2 to v2.
    11. The removal step removes a from the role.
    12. A developer pushes v3.
    13. The publish job starts with its catch-up pass.
    14. The removal step runs and removes nothing.
    15. The publish check passes.
    16. WorkOS creates the permission c.
    17. WorkOS adds c to the role.
    18. The WorkOS steps end.
    19. An operator holds I2 on v2.
    20. The store saves v3.
    21. The pass upgrades I1 to v3.
    22. The removal step removes b, because T2 of v3 needs b. The members of I2 lose T1 and T2, which v2 gives them through b.

    This is the cause of path 3, in the move sequence. The check again under the store lock refuses this store.

Paths 6 to 8 occur if the WorkOS steps add to the role only the permissions that the same run creates. The current text adds each permission that the role lacks, also when it exists in WorkOS, so it closes them.

  1. No store before its WorkOS steps, then no loss and converge (Move sequence, 6, 7, 9 steps). The role never gets a permission that already exists in WorkOS.

  2. No store before its WorkOS steps, then converge (Drop in place sequence, 15, 18 steps). A permission that v3 gives back is never added again.

    1. Start: v1 is stored. I1 and I2 are on v1. The role holds a and b.
    2. A developer pushes v2.
    3. The publish job starts with its catch-up pass.
    4. The removal step runs and removes nothing.
    5. The publish check passes.
    6. The WorkOS steps end.
    7. The store saves v2.
    8. The pass upgrades I1 to v2.
    9. The pass upgrades I2 to v2.
    10. The removal step removes a from the role.

    12. The publish job starts with its catch-up pass.

In the spec

The Removal step section of Publish, which Reconcile replaced, stated the early grant of paths 1 and 2 as an accepted window: the access is what the newest version grants, and only an operator's hold makes it last. It also noted the over-grant with 2 held installations, which this model did not check. See "What the model leaves out".

Readings

  • "Stops on an older version after the store": the model accepts a loss only when the hold starts after the store. Under the current text, a hold before the store refuses the publish, so no other case remains.
  • The spec accepts early access during the window from the WorkOS steps to the upgrade of the installation, also after a stopped job or a refused store. A held installation keeps it while it is held (paths 1 and 2).
  • The over-grant window ends at the next removal step for the newest version. That step can be in the catch-up pass of the next job.
  • The catch-up pass runs the removal step, because each upgrade call that ends with nothing behind runs it.
  • A publish with the same grants file as the newest version makes no new version, runs no WorkOS step, and goes to the pass.
  • The check refuses a behind installation first, then PermissionInUse. The spec gives no order between the 2.

What the model leaves out

  • RoleInUse, and a grants file that adds or removes a default role. The 1 role always exists.
  • Permissions of the Ontology service, custom roles, and Action Types with their check of Object Type permissions.
  • Install, a hold of I1, and 2 held installations at a time. So the model does not test this case for No over-grant: 1 held installation on a version that gives p, 1 on a version that maps a type to p and does not give it, and a newest version that drops p and has no type that needs it. The spec states this case as an inference, and accepts it.
  • Upgrade failures on data, lock waits, time limits, and the limit of 3 sweeps. A pass can sweep again without limit, or stop.
  • The cache of WorkOS answers in each instance. The model gives a member the new role at once, not within 60 seconds or 5 minutes.
  • A pushed commit that no job publishes, and a rerun of an older commit. A new run repeats the same grants file.
  • validateOnly, the static problems of the grants check, and the descriptions of permissions.
  • A replay of each path against code. The model describes the spec, not code.
