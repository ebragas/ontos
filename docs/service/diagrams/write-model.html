The write path model

A write of an Action runs in 1 transaction of Db.transaction, and writeEdits turns its failure into the answer (Storage "Writes"). This TLA+ model checks what the caller is told when the transaction fails at each step. It has 2 Actions that edit 1 Object, and each Action loaded version 0 of it. A body can fail, the server can end the session with 25P04 (transaction_timeout) or 57P01 (an admin shutdown), and the connection can drop after COMMIT is sent. At COMMIT, the commit can apply or not before a dropped connection or a 57P01. A 25P04 comes only before the commit applies: in PostgreSQL 17, CommitTransaction in src/backend/access/transam/xact.c holds interrupts and turns off the transaction timeout before RecordTransactionCommit, and the timeout of the write is local to its transaction, so it is 0 after the commit. The model comes from packages/service/src/db/index.ts and packages/service/src/actions/write.ts. TLC checked 219 states and 570 steps.

Rules

  • Holds. No lost update: both Actions loaded version 0, so at most 1 write commits. The second Action locks the Object after the first one ends, finds the newer version, rolls back, and gets 409.
  • Holds. A refusal wrote nothing: a 409 or a 400 tells the caller that nothing was written. A rule-backed Action runs again on a 409.
  • Holds. A 200 means that the write committed.
  • Holds. An answered write holds no row lock.
  • Holds. A connection whose session ended never goes back to the pool. A failed ROLLBACK occurs only on an ended session, and the pool drops that connection.
  • Holds. No deadlock: each path ends with an answer to both Actions.

A case that the model raised

A first model let the server end the session with 25P04 after the COMMIT applied. Then writeEdits would answer 400 ActionDeadlineExceeded, and the row would be written. The PostgreSQL 17 source above rules that path out, so the model now sends 25P04 only before the commit applies, and each rule holds.

What the model leaves out

  • A deadlock: the model has 1 Object, so 2 Actions never lock in a cycle. The overlap tests of packages/service/src/db/versions.sql.test.ts and the deadlock test of packages/service/src/functions/links.sql.test.ts carry it on Postgres.
  • A ROLLBACK that fails on a live connection. pg rejects a query on a live connection only for an error of the statement, and ROLLBACK has none.
  • The deadline check of writeEdits after a body failure, which can turn a 500 into a 400. It runs before COMMIT, so no write has applied.
  • Reads, streams, and Db.snapshot, which write nothing.

The model is not stored. To check it again, write a TLA+ specification from the code and this page and run TLC.
